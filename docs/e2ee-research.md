# Integration update

The product now uses live room delivery without server body storage, offline mail,
participation IDs, or automatic send retries. See [the current contract](delivery-reliability.md).
The cryptographic research below remains exploratory; its queue/key-retention
integration proposals are superseded. No E2EE implementation is included.

# Tandry 会话级端到端加密研究

研究日期：2026-09-16。状态：设计建议与隔离实验，尚未实现生产接入。

## 结论

建议第一阶段验证“每个 Agent 会话独立密钥、逐条定向加密”的实现，
以 RFC 9180 HPKE Auth 模式作为候选。它适合目前的离线收件箱和消息重试，
无需新建群组密钥系统，也无需设备迁移、历史恢复或完整的双棘轮状态机。

这个候选有两个必须明确的限制：

1. 首次公钥分发若只信任 Hub，就不能抵御 Hub 在首次接触时替换公钥。
   自动使用可以采用 TOFU，但需提供独立渠道核验指纹的路径；严格模式在核验前不收发用户正文。
2. HPKE 不提供接收方密钥泄露后的历史前向保密。会话私钥后来泄露，
   攻击者可解密之前保存的该会话密文。它不等价于完整 Signal 协议。

若产品要求默认同时抵御主动恶意服务器和未来端点密钥泄露，应转向完整的
身份信任与棘轮协议方案，不能把 HPKE 候选直接升级宣传为具备这些保证。

## 已确定的产品约束

- 只使用 `~/.tandry`，尊重 `TANDRY_HOME`，不考虑旧目录迁移。
- 加密身份属于 Agent 会话，不属于项目目录或共享登录凭据。
- 新设备、新会话、分叉会话产生新身份；不继承旧会话消息或密钥。
- 同设备恢复同一个会话，使用原来的本地身份和密钥。
- 换账号或 Hub 时隔离身份，登录令牌刷新不应更换加密身份。
- 不做跨设备历史同步、恢复短语、平台密钥托管或账号级解密万能钥匙。
- 加解密在 Bridge 完成；模型只使用消息工具，不接触密钥参数。
- “主动读取”和“实时接收”只是投递方式，不改变加密边界。

## 当前代码可以复用什么

| 位置 | 当前行为 | 加密接入需要的调整 |
| --- | --- | --- |
| `packages/bridge/src/runtime.ts` | 按宿主、会话、账号绑定身份；按 Hub、房间恢复 journal | 在发件入队前解析并固定加密收件人；在入收件箱前完成验证 |
| `packages/bridge/src/config.ts` | 本地稳定 `ref`，新会话创建身份 | 同步创建和恢复密钥；密钥缺失不能在原身份上静默重建 |
| `packages/bridge/src/delivery-store.ts` | 原子替换、fsync；持久化 unread、seen、outbox | 保存精确的加密信封；用认证后的逻辑消息 ID 去重 |
| `packages/bridge/src/hub-client.ts` | WebSocket 重连、请求匹配、ACK | 传输独立的加密 wire 类型，不把密文伪装成普通正文 |
| `packages/protocol/src/index.ts` | 明文 send/message、六位 ref、64 Ki 字符正文限制 | 引入版本、加密信封、完整密钥指纹、字节限制和错误类型 |
| `packages/hub/src/room.ts` | 在 Hub 解析昵称，绑定收件人；认证投递和 ACK | 增加公钥目录、精确地址和加密能力约束 |
| `packages/hub/src/store.ts` | 正文及去重 payload 入库，事务内提交 | 改为密文及信封摘要；公钥绑定不能随在线状态消失 |

这些是对当前工作区代码的观察，不代表已部署版本或完整安全审计。

有两项容易遗漏的现状：

- 首次发送的昵称解析发生在 Hub，只有接受后才固定收件人。E2EE 必须先知道
  对方公钥，因此应把首次解析提前到 Bridge。重试不能重新按昵称寻找其他会话。
- 接收端目前按 Hub 分配的 `message.id` 去重。恶意 Hub 换一个 ID 后重放密文，
  仍可能造成第二次入箱。需要新增发送端生成、受密码学认证的逻辑消息 ID。

## 协议与依赖比较

| 方案 | 适配情况 | 主要代价或限制 | 研究判断 |
| --- | --- | --- | --- |
| 完整 Signal 协议 / libsignal | 定向异步通信、密钥演进 | Rust 原生扩展、状态机与预密钥管理；第三方使用不受上游支持 | 强保护路线的候选，先做跨宿主和分发评估 |
| HPKE Auth，每条消息独立上下文 | 对方离线时也能加密；重试和乱序处理简单 | 不含应用层身份信任、去重、降级保护；无接收方前向保密 | 推荐作为第一阶段技术候选 |
| MLS | 动态群组密钥协议 | 我们目前主要是同房间内定向通信，群组状态和成员提交会增加复杂度 | 有全员共享消息需求时再评估 |
| libsodium sealed box | 简单的接收方加密 | sealed box 不验证发送者身份，不能直接作为 Agent 指令来源证明 | 不单独采用 |
| 自己组合 ECDH、HKDF、AES | 平台基础 API 可用 | 应用团队承担协议组合正确性和互操作维护 | 不自行重写 HPKE 或棘轮 |

HPKE 的能力边界见 [RFC 9180 §9](https://www.rfc-editor.org/rfc/rfc9180.html#section-9)。
使用 Auth 模式不等于数字签名或第三方可验证的消息来源证明；DHKEM Auth 还存在
接收方密钥泄露时的冒充边界。此候选假设端点密钥未失陷。
[libsignal](https://github.com/signalapp/libsignal) 明确说明其外部使用不受支持，
Node 包包含原生组件，许可证为 AGPLv3。这里记录许可证事实，未作法律兼容性结论。
[sealed box 文档](https://doc.libsodium.org/public-key_cryptography/sealed_boxes)
明确其不提供发送者身份认证；[MLS 架构](https://www.rfc-editor.org/rfc/rfc9750.html)
可用于后续群组方案评估。

## 建议的数据和身份模型

### 本地密钥

在 `~/.tandry/crypto/` 下保存按宿主、宿主会话 ID、Hub 来源和不可变账号 ID
隔离的记录。身份中增加随机至少 128-bit 的实例标识；现有六位 ref 只是路由短码，
不能作为密码学指纹或唯一信任根。

候选使用一对会话级 P-256 KEM 密钥。固定套件为 DHKEM(P-256, HKDF-SHA256)、
HKDF-SHA256、AES-256-GCM，Auth 模式；每条消息创建独立上下文。
这是减少原生扩展和额外算法依赖的实现选择，不意味着其他曲线不安全。
第一版不协商算法降级，也不加入实验性后量子扩展。

密钥记录须在首次公开身份前持久化；目录 0700、文件 0600，原子写入与 fsync。
单个会话只允许一个运行中的密钥/journal 写入者。文件丢失或损坏时返回明确错误，
用户新建会话后重新加入，不在相同实例标识下悄悄生成新密钥。

权限受限的文件是最低限度的端点存储方案，不是本地静态加密。
系统钥匙串、Linux 无桌面密钥服务及本地 journal 加密要单独评估；
不能把与密文放在同目录的可读解密密钥宣传为抵御本机入侵。
本研究的端点假设是宿主及其运行账号可信。

### 公钥目录与信任

公钥描述绑定 `Hub / roomInstance / accountId / conversationInstance / ref / keyId / suite`。
`keyId` 使用规范化公钥编码的完整 SHA-256 指纹；不使用可修改昵称建立信任。
roomInstance 独立于可重用的房间码，并且在同一房间生命周期内稳定。

Hub 注册时认证账号并验证密钥持有证明，固定同一实例的公钥。
密钥持有证明须使用专用协议域和一次性、有期限的挑战；具体报文另行设计和验证。
它防止普通客户端随意声明密钥，不证明首次公钥属于真实世界中的某个同事。

Bridge 保存已经见过的公钥绑定；相同实例发生变化时阻止收发，而非自动重绑。
必须先加密验证，再把自称的 accountId、ref 和名字当作消息来源。
新实例即使同账号、同名，也不继承旧实例的“已核验”状态。

提供两个可明确区分的信任状态：

- 首次信任 / TOFU：自动记住首次公钥。只依赖服务目录建立初始身份，
  不声称抵御首次联系时已被控制的 Hub。
- 已独立核验：通过当面、已认证的其他通信渠道比较完整指纹或其安全编码。
  严格模式在核验前暂停正文收发；状态应由本地客户端记录，不能由 Hub 单方面授予。

核验不能只通过同一个未核验的 Tandry 房间完成，也不能让 Agent 因为工具描述说
“可信”就替用户完成核验。房间码不是密钥、指纹或共享加密秘密。
未来若要求新会话也无感继承可信身份，必须再引入可独立验证的签名授权链，
这会扩展当前会话独立的产品模型，暂不加入。

公钥绑定及必要 tombstone 的保留期必须覆盖未投递消息和去重窗口。
`RoomStore` 存在清理离线 session 行的接口，身份绑定不应附着在可清理的在线状态上。

## 一条消息的流程

1. Bridge 解析昵称为唯一、精确的会话描述，并检查公钥信任与加密能力。
   若离线时有已固定的目标及公钥，可继续加密入队；若无法解析，则返回需要连接，
   不把明文交给 Hub 或在恢复连接后重新猜测收件人。
2. Bridge 生成 UUID 逻辑消息 ID，建立独立 HPKE Auth 上下文，进行一次 seal。
3. 将版本、套件、双方完整身份和 keyId、roomInstance、逻辑消息 ID、消息种类
   以及需要防篡改的选项纳入规范编码的 AAD。使用有固定顺序的字段数组或明确的
   二进制编码，不依赖任意 JSON 对象的属性顺序；具体字节格式需在协议实现前固定。
4. 在出网之前，原子保存完整密文信封和固定收件人。重试逐字节重发原信封，
   不重新 seal、不更新逻辑 ID、不按昵称改收件人。
5. Hub 校验账号、房间成员、信封长度、精确路由和所声明的 keyId，再原子保存信封
   与 `(senderInstance, clientMessageId)` 去重条目。摘要覆盖完整固定信封，禁止同 ID
   不同密文或收件人。Hub 不执行正文解密。
6. 接收 Bridge 验证信任、上下文和 Auth 密文，再按
   `(roomInstance, senderInstance, senderKeyId, clientMessageId)` 去重。
   同逻辑 ID 不同信封判为冲突，不作为新消息交给模型。
7. 验证后的消息与 seen 标记一起 fsync 成功，才发 transport ACK。
   同一合法消息被再次投递时可再次 ACK，但不重复入箱。
8. 读取工具沿用当前宿主语义。传输确认不等于模型已读取、理解或执行任务。

Hub 生成的 ID 仍用于投递 ACK，不负责加密真实性。
如果未来需要端到端确认收件，使用接收会话认证的独立 receipt 类型，
不要将 Hub 声称的 acknowledged 展示为密码学证明。

暂时未知的公钥不能仅凭信封自带公钥获得信任。离线收件人第一次看到发送方时，
需要按同样的 TOFU/独立核验规则处理；已核验缓存不依赖发送方当时在线。

错误消息应区分协议不支持、公钥未核验、公钥变化、密钥丢失、认证失败和存储失败。
坏密文不能进入模型上下文；可以有受限的本地隔离记录和明确拒收状态，
不能伪造“成功接收”。其重试和最终失败规则应防止坏消息永久堵塞收件箱。

## 云端必须同时改的地方

- `messages.body` 与 `send_keys.payload` 都存在正文副本，必须一起改。
  不能只加密主表而把正文留在去重、错误日志或 Trace 中。
- 单独定义 `EncryptedEnvelope` 和本地解密后的消息类型；加密房间不接受任意明文 fallback。
  加密模式须由本地选择/固定，不能仅信任 Hub 可修改的能力标记。
- 目前 `body.max(64 * 1024)` 限的是 JS 字符数。实验中 65,536 字节正文的
  AES-GCM 密文为 65,552 字节，Base64 后 87,404 字节，另有 65 字节 encapsulation
  和头部。要明确 UTF-8 正文限制、wire 限制和总存储限额，不能直接塞回旧 body 字段。
- 正文存储预算应按实际信封/密文字节统计；字段、JSON 解析、候选公钥和坏消息都有上限。
- 服务通知、idle-notice、成员状态继续属于 Hub 声明的元数据，应标识为服务事件。
  当前 idle-notice 使用同事 ref 的表示方式需要调整，避免看起来像同事认证的加密消息。
- 成员退出后 Hub 拒绝新投递；已交付密文和已有私钥无法远程撤回。
  定向密钥方案不依赖全房间共享密钥，因此正常退出不需要全房间重建群密钥。
- 元数据仍可能暴露账号、房间、时间、消息大小、hostname/cwd/repo，E2EE 不隐藏这些字段。
  减少项目路径等元数据是独立的数据最小化工作。

## 接入形态和上线顺序

本地 Codex、Claude、Pi、OpenCode、DSH 复用 Bridge 加密实现，宿主工具继续使用正文。
网页版 ChatGPT 若把正文传给 Tandry 托管 MCP，该服务仍能读取正文，
即使随后 seal 也不满足“Tandry 不可读”。用户控制的网关可以成为受信端点，
但它对 ChatGPT 返回的正文仍进入模型提供方处理范围。

加密房间应拒绝不具备相应能力的托管连接和旧客户端，不能自动解密转发。
只发消息模式不会消除发送端托管服务接触明文的问题。

建议上线顺序：

1. 先验证候选套件、严格报文格式、公钥持有证明、信任流程和跨宿主包兼容性。
2. Hub 先支持新版本与独立加密房间，随后发布客户端；旧客户端不能进入加密模式。
3. 用新建加密房间试运行。既有明文房间的转换、历史处理和密文/明文混用不属于第一阶段。
4. 升级只影响新消息；不能承诺旧正文及备份被追溯加密或立即消除。
5. 完成安全评审和故障验收后，才调整用户可见的安全承诺。

这是部署顺序建议；本研究没有执行部署、发布、迁移或生产调用。

## 隔离实验结果

脚本：[research/hpke-probe.mjs](research/hpke-probe.mjs)。仅使用合成身份和消息，
不访问真实账号、Hub、`~/.tandry` 或项目依赖。

在 Node **22.23.2** 和 **24.20.0**、`@hpke/core` **1.9.0** 上均通过：

- 14 组实验检查，包括 Auth 收发、错误双方密钥、Auth/Base 替换、协议域替换、
  房间/双方会话/逻辑消息 ID 篡改、密文与 encapsulation 篡改、独立随机封装、
  信封序列化恢复、私钥恢复、重放行为、64 KiB 正文和 CommonJS 导出加载。
- 来自 CFRG HPKE 仓库的一个 Auth/P-256/HKDF-SHA256/AES-256-GCM 向量，
  顺序解密并校验其中 **257 条**消息。不是 257 个独立套件向量，也未验证全部 HPKE 套件。
- 重复 open 同一信封成功，说明应用层去重不可省略。
- 恢复接收私钥后可以解开旧信封，符合此方案不提供接收方前向保密的边界。

向量来源固定为 commit `5f503c564da00b0687b3de75f1dfbdfc4079ad31` 的
[test-vectors.json](https://github.com/cfrg/draft-irtf-cfrg-hpke/blob/5f503c564da00b0687b3de75f1dfbdfc4079ad31/test-vectors.json)。
实验筛选 `mode=2, kem_id=16, kdf_id=1, aead_id=2`，所保存单向量 JSON 文件的
SHA-256 为 `dc35208703756d9be87e6a59d2454dbc0e17e3c3496e1a2767faecad8caf137b`。
该摘要依赖 JSON 序列化格式，语义等价但空格不同的文件可能摘要不同。

最小复现，不改变仓库依赖：在临时目录复制 probe，运行
`npm install --ignore-scripts --no-audit --no-fund --save-exact @hpke/core@1.9.0 @hpke/common@1.10.0`，
再运行 `node hpke-probe.mjs`。提供筛选后的向量文件作为第一个参数，可复现上述向量解密。

没有执行完整 Hub/Bridge 集成、磁盘故障注入、Bun 实测、最终插件打包、OS 钥匙串接入，
也没有证明公钥目录能抵御主动恶意服务器。实验是依赖可行性证据，不是生产安全认证。

| 信任 | 首次状态明确；同实例换钥拒绝；新实例不继承核验；伪造目录不能绕过本地固定 |
| 路由 | 同名歧义拒绝；首次加密后固定收件人；房间码/ref 重用不跨实例收件 |
| 真实性 | 篡改正文、身份、版本、套件、选项、AAD 均拒绝；服务消息不冒充用户消息 |
| 重放 | 换 Hub ID、重复 welcome、丢 ACK、读后重启，都不重复入箱；逻辑 ID 冲突被检测 |
| 持久化 | 出网前信封已落盘；接收写失败不 ACK；收发过程中断电后可恢复 |
| 并发 | 同会话多个进程争用被阻止；切换会话后的旧异步加密回调不能提交到新 journal |
| 离线 | 首次离线收件；已有可信公钥的离线发送；公钥目录保留覆盖积压消息 |
| 边界 | Unicode 字节计数、密文膨胀、坏消息、满配额和密钥目录滥用都有上限 |
| 数据暴露 | 所有 Hub 表、去重字段、日志、Trace 中没有实验正文或端点私钥 |
| 兼容性 | Node 22、各宿主实际运行时、Bun、CJS/ESM 及导出的自包含插件包 |
| 产品 | TOFU/已核验的措辞准确；无静默明文回退；传输 ACK 不等同任务执行 |

第一阶段候选可推进到实现验证，但“采用无前向保密的 HPKE”和“默认首次信任目录”
仍是产品安全边界的选择，不能从本研究自动推定为用户已接受的最终上线承诺。
