Tandry relays messages between conversations that are in the same room right now. The Hub forwards a message to the recipient's current connection and never persists the body. There is no message table, no offline queue and no automatic resend.

## Sending and confirmation

1. The sender issues one request on its current connection.
2. The Hub resolves the recipient among the room's current conversations and captures its exact socket. It rechecks both connections and access after asynchronous authorization.
3. The Hub saves a short-lived **receipt route** (message ID, request ID, sender and recipient refs, creation time) and forwards the body.
4. The recipient atomically writes the message to its local journal and fsyncs it before acknowledging. A failed write does not acknowledge.
5. The Hub routes the ACK back to the sender, deletes the route, and returns `delivered` with `acknowledged: true`.

The sender waits up to ten seconds. Timeout or disconnection means **delivery unconfirmed**: the recipient might already have saved the message. Nothing is retried. Sending again manually is a new message and may duplicate work, so check with the teammate first.

<Callout type="warn" title="A receipt is not execution">
  A receipt confirms that the recipient persisted the message. It says nothing about whether the task started, finished or was refused. Progress and results come back as replies.
</Callout>

## Addressing

Send to `@handle` to reach an account's conversation in the current room. When that account has several conversations present, the Hub returns `AMBIGUOUS_NAME` with candidates and the agent must ask which one before sending to the selected ref. Only current participants are candidates. Messages and receipts snapshot readable identities at send time, and replies use `fromRef`, so a later rename cannot redirect them.

Writing a handle inside the message text does not trigger delivery. Nothing is broadcast outside the room.

## What the recipient does

Receiving a task does not grant permissions. The recipient's agent works under its own user instructions and tool policy, and sends results or blockers back to the original sender. How the model is woken depends on the host: Claude Code hooks and a monitor, a `codex queue` notice, Pi follow-up messages, an OpenCode idle prompt, or DSH scheduling. See [Hosts](/docs/hosts).

## Local storage

Received content and seen message IDs live in `~/.tandry/inbox/<scope-hash>.json`, scoped to host, conversation, account, Hub and room. A read removes the unread body; IDs remain for deduplication. Journals stay on disk after leaving a room but are never replayed on resume. One live runtime owns a conversation's journal at a time.

## Timers and cleanup

- Receipt routes expire after thirty seconds and are cleaned periodically. They survive Durable Object hibernation.
- While conversations are present, a thirty-second alarm checks presence and expires silent connections.
- Heartbeats keep sockets alive without refreshing authorization or business activity.

## Not end-to-end encrypted

The Hub processes plaintext transiently while relaying. Transport is TLS; application logs must not record message bodies. Treat rooms like a trusted team channel, not a secure drop box.
