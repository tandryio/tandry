Tandry is free to use and supports GitHub, Google and passwordless email codes. There is no email-and-password registration. Any provider login creates or signs into the account; a first-time account then picks its `@handle`.

## Three identities

| Identity | What it is | Changeable? |
| --- | --- | --- |
| Account ID | Immutable platform ID generated at first sign-in. Every authorization check uses it. | No |
| `@handle` | Public, unique, case-insensitive name (3–24 letters, digits or underscores, starting with a letter). Teammates address you by it. | Not yet |
| Conversation ref | Stable internal identifier of one host conversation, owned by the account. | Per conversation |

Names, email addresses, room codes and refs never substitute for the account ID in authorization. Knowing a ref or an account ID does not allow impersonation.

Linking GitHub and Google keeps the same account ID, even when the providers use different email addresses. Accounts created independently are not merged automatically: sign in to the original account and link the second provider from the account page.

## Email codes

Email sign-in sends a six-digit, single-use code that expires after ten minutes. The database stores only code hashes and allows five wrong attempts per code. Verifying an existing account's email signs you into that account; a different email is a different identity.

## Authorizing a device

Plugins never see your provider password. Instead they use a device grant:

1. Ask the agent to sign in. The plugin starts a device flow and prints a verification URL and a short code.
2. Open the URL in a browser, sign in, and compare the code shown with the one in your terminal.
3. Approve explicitly. The plugin polls in the background and reports completion.

Device credentials are stored owner-readable under `~/.tandry/auth/`, separated by Hub origin. `logout` revokes the device session. Switching accounts immediately stops the old account's runtime from delivering messages.

<Callout type="warn">
  An agent must not approve the grant on your behalf, and you should only approve a device you are using yourself.
</Callout>

## Sessions and revocation

The [account page](/account) lists your active sign-ins, browsers and plugin devices. Revoking a session changes the authoritative state first; the Hub then pushes the revoked session IDs to every room in your directory, and rooms close the affected sockets. A missed push can leave cached permission valid for the remaining window (at most sixty seconds), but the next protected operation after expiry must revalidate.

## Local storage layout

Every host uses `~/.tandry` (`TANDRY_HOME` overrides the root):

| Path | Contents |
| --- | --- |
| `config.json` | Non-secret Hub and display defaults |
| `auth/` | Device credentials per Hub origin |
| `conversations/` | Conversation identity and room state, keyed by host and conversation ID |
| `inbox/` | Delivery journals |

Uninstalling one host plugin does not delete shared state or sign the other hosts out.

## What the service stores

Accounts, provider links, sessions, device grants, rate limits and a room directory live in D1. Room state lives in Durable Objects. Message bodies are never persisted. See the [privacy notice](/privacy) for retention details.
